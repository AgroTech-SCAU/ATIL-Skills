# 汇报信息标准化

将工作分成“去之前怎么安排”和“完成之后怎么汇报”两部分；保持计划与实际的任务对应，便于判断、执行和跟进

## 两部分与模板选择

- **事前安排**：说明目标、时间地点、人员车辆、统一联系人、设备准备、任务分工、执行办法与预期成果；需要可填写版本时读取 [事前安排模板](references/field-plan-template.md)
- **事后汇报**：先交代总体结果，再逐项对照原计划写实际结果、成果证据、问题偏差、后续安排与协调请求；需要可填写版本时读取 [事后汇报模板](references/completion-report-template.md)
- 用户要两份模板时一起提供；只整理某一阶段时，只读对应模板，不强行同时输出两份
- 进行中的进展汇报采用事后汇报的结构，明确哪些已完成、进行中或受阻，不伪装为最终结果

## 信息标准

按下表检查与当前事项有关的信息；这些是内容检查维度，输出采用下文的分点格式，用户另有格式要求时优先遵循

| 信息 | 应说明什么 | 需要避免的模糊表达 |
|---|---|---|
| 事项与目标 | 要做什么、为什么做、本次具体解决或验证哪个问题 | 去看看、推进一下、做个实验 |
| 时间与节点 | 具体日期、必要的起止时间；任务截止时间、准备完成时间或下次反馈节点 | 周六、近期、尽快，却没有可落实的时间 |
| 地点与对象 | 去哪个具体地点、与谁对接、针对哪台设备或哪个版本；远程工作可写系统或环境 | 那边、现场、这个设备，且上下文无法唯一识别 |
| 人员与分工 | 谁牵头、谁参与、谁配合；各组或各人的任务、人数及参加状态 | 我们、他们负责，却没有可跟进的责任人 |
| 任务与执行安排 | 做哪些具体动作、先后顺序、各组如何配合、前置条件是什么 | 人到了再说、现场再安排 |
| 资源与准备 | 所需设备、材料、数据及其准备状态；外出时补车辆、搬运、供电等实际需求 | 带设备去，却未说明设备清单或是否可用 |
| 交付与判断依据 | 最终交回什么、何时交回、凭什么判断完成；已完成工作给实际结果及证据 | 调试好了、效果不错，却没有结果或可检查的材料 |
| 问题与协调请求 | 哪些未确定或受阻、影响什么、需谁提供什么支持或作什么决定、何时需要答复 | 有点问题、还在协调，却没有具体请求 |

上述八项是基于会议要求整理的复用规范，不是领导逐字列出的八项制度；涉及会议原意或需要回查时读取 [会议依据与示例](references/meeting-basis.md)

## 整理方法

- 先选择事前安排或事后汇报；进行中使用进展版，优先采用用户要求的篇幅和格式
- 从用户材料及当前对话中提取已有事实，再用信息标准检查缺项；不要为凑齐字段引入无关事项
- 先交付一版可用汇报，再列影响执行、判断或决策的关键缺项；不要因为信息不全只回复问题清单
- 未提供的信息写“待确认”或“未提供”；建议用“建议”标明，不能伪装成既定安排
- 区分“拟定／待确认”“已确认”“进行中”“已完成”“部分完成”“未完成”“未开展”“待验证”“受阻”等实际状态；不能把预计参与写成已确认，把计划写成完成
- “周六／明天”等相对日期仅在基准日期明确时转换为绝对日期；保留推算依据，无法唯一确定时保留原表达并标待确认，不擅自补钟点
- 人名、地名和技术名词识别不可靠时标记待核；无法可靠区分说话人时，不擅自归属发言
- 负责人应落实到可跟进的人或已明确负责的角色；材料只写某组时可以保留组名，不自行分配个人
- 允许写“验收标准待确认”，或提出标明为建议的验证办法；不自创数量、准确率、预算或截止日期

## 排版与任务对应

- 默认使用 Markdown 分级标题和简洁分点，段落之间留一空行；正文不默认加粗，也不包在代码块里；用户明确要求微信纯文本、一段话、表格或其他格式时按要求输出
- 文档标题使用 `# 日期（星期）地点／事项工作安排` 或 `# 日期（星期）地点／事项完成情况汇报`，进行中相应改为“进展汇报”；一级章节用 `## 1. 标题`，二级用 `### 1.1. 标题`，三级用 `#### 1.1.1. 标题`，编号末尾保留点；按内容使用层级，不为凑齐三级而添加空标题
- 文档标题后、每两个一级章节之间各放一条独占一行的 `---`，前后留空行；二、三级标题之间不加分隔线，文末不额外追加分隔线或“总结”段
- 事前默认顺序为：1. 时间、2. 地点、3. 人员、车辆与联系、4. 设备与准备、5. 本次目标、6. 任务分工、7. 现场执行安排、8. 预期成果与反馈；有协调请求时增加9. 需协调事项
- 事后默认顺序为：1. 总体结果、2. 各项任务完成情况、3. 问题分析、4. 后续安排；实际执行变化可放在总体结果下，成果名称、数量、存放位置和检查状态可放在对应任务的实际结果中；材料较多时可另设实际执行情况、成果与存放位置或需协调事项等章节
- 一级章节按实际内容增删并连续编号；“总体结果”保留必要的完成与未完成概览，文末不再重复总结
- 地点区分出发地与目的地，有多个出发点时分别列出；人员写总人数及姓名，不从名单顺序推断上车地点、分组或负责人
- 车辆与人员放在“人员、车辆与联系”：车辆安排采用打车请求写法，本模板为“需要麻烦赵博打【数字】辆车”；当次另有安排人时按用户提供的信息替换，不能把请求写成已安排
- 每辆车分别写“车辆 1 出发地：【具体上车地点】、联系人：【姓名】【电话号码】”，按实际车辆数量增删；未提供的数量、地点和联系方式保留具体占位，不从名单顺序推测谁乘哪辆车
- 各车联系人随对应车辆列出；其他现场对接人仍集中在“人员、车辆与联系”内，同一人已列为车辆联系人时引用对应车辆，不重复抄写联系方式；只使用本次提供的联系方式，不从旧案例带入；已明确的装载需求按需补充
- “设备与准备”列设备及配件、检查充电、提前搬运、准备责任人与时间，以及供电、网络、软件等前置条件
- 事前先以“本次目标”建立任务列表；目标、分工、执行和成果中，同一任务保持相同任务编号、名称和顺序，分别说明目标、责任人、执行办法、交付物；章节前缀随所在章节变化，例如第二项任务对应 `5.2.`、`6.2.`、`7.2.`、`8.2.`
- 任务数量由实际材料决定，不固定为五项；名称相近但用途或交付物不同的任务不要擅自合并；事前任务增删后同步调整目标、分工、执行和成果各节中的任务编号
- 事后在任务完成情况、成果、问题分析和后续安排中沿用事前的任务名称、任务编号及顺序；每项原任务均交代状态，临时新增任务另列并注明，不用新增成果替代原任务的交代；某项无问题或无后续时可省略对应条目，但保留其他任务的编号末段，不重新排序
- 已有数量、单位、格式和预期标记应准确保留，例如“各 50 条”“预计 100 张”“约 15 GB”；设备型号和术语不凭猜测纠正
- 缺项直接放在相应位置，写为 `【待补充：具体需要填写的信息】`；已明确存在但未落实的事项可写 `【待确认：具体事项】`，不要只给一串笼统空栏
- 对照执行安排检查设备准备、任务分工和成果是否匹配；例如执行提到电脑而设备清单未列时，标记是否需携带待确认，不擅自断言已准备；列出的参与者未对应任务时，可提示补充角色，不自行为其分工

两份模板中的日期、人员、设备及数量均需来自本次材料；占位符用于待填写内容，不是需要原样提交给领导的固定文字

## 按汇报阶段调整重点

### 事前安排

重点说明目标、时间地点、负责人、分工、准备状态和预期交付；涉及外出时检查谁去、怎么去、带什么、现场做什么实验，以及需要协作的组是否参加；车辆和全部联系人按上述规则与人员合并

### 事后汇报

- 总体结果先写主要完成什么、哪些部分完成/未完成/未验证及关键影响因素；不能因为活动结束就写“任务全部完成”
- 实际执行情况中的人员和车辆合并填写；联系人变动或出现对接问题时补充，不重复已经共识的全部行程背景
- 逐项对照原目标、预期数量或标准，给出实际数量、测试条件、观察结果、结论和完成状态；原计划缺失时标未提供，不从实际结果倒推原目标
- 成果写文件/数据/代码/图纸/视频的名称、数量、必要版本、链接或路径、整理人及检查状态；“采集数量”和“检查后可用数量”分别记录，尚未检查写“待检查”，不自行声称质量合格
- 失败测试也保留条件、现象和证据；区分已确认原因与待排查线索，局部验证只支持对应结论，不外推为整机或完整流程通过
- 偏差说明相对原计划少做、改做或新增了什么及其影响；后续安排写谁做什么、交付物、反馈节点与前置条件；没有实际后续工作时不强造新任务
- 协调请求写清需谁支持或决定什么、希望何时落实及未落实的影响；进行中的进展版同样遵循这些规则

## 默认交付

先给可直接复制的分点汇报稿；用户需要交给他人补充时，将具体占位符放进正文对应位置，避免另列重复的缺项清单；只对影响执行或理解且不适合放正文的问题补充简短提示

用户只要求检查时，指出关键缺项并给出修改稿；用户明确要求一段话、表格或其他格式时按要求输出

仅整理、检查和起草汇报；发送消息、创建日程或分配任务需要用户另有相应指令
